## 二、开发隔离规则（三大铁律）

### 规则1：表归属 = 代码归属

**谁建表，谁就负责该表的 Entity + Mapper + Service（含所有写操作）。**

```
B 拥有 elderly 表
  → B 写：Elderly.java, ElderlyMapper.java, ElderlyService.java, ElderlyServiceImpl.java
  → C 绝对不能写：@Autowired ElderlyMapper（编译过了也不行！）
```

### 规则2：跨域读取 = 注入对方的 Service

```java
// ✅ C 需要读老人信息 — 注入 B 的 Service（只读调用）
@RestController
public class WarningController {
    @Autowired private WarningService warningService;   // C 自己的
    @Autowired private ElderlyService elderlyService;   // B 提供的，只能调读方法

    @GetMapping("/warning/{id}")
    public CommonResult getDetail(@PathVariable Long id) {
        WarningRecord warn = warningService.getById(id);
        Elderly elder = elderlyService.getById(warn.getElderlyId());  // 跨域只读
        return CommonResult.success(Map.of("warning", warn, "elderly", elder));
    }
}
```

### 规则3：公共设施 A 独建，B/C 只使用

```
common/config/     → A 维护
common/result/     → A 维护
common/exception/  → A 维护
common/enums/      → A 维护
aop/               → A 维护
pom.xml            → A 维护（B/C 需新增依赖时告知 A）
application.yml    → A 维护（B/C 需新增配置时告知 A）
```

## 三、跨域接口契约

### 开发前必须对齐的接口

每个阶段的开发开始前，三人花 **15 分钟** 对齐所需接口：

```markdown
## B 提供给 C 的只读接口
- [ ] ElderlyService.getById(Long id)          → C 做预警详情时需要
- [ ] ElderlyService.listByDoctorId(Long id)    → C 做随访选择老人时需要
- [ ] HealthRecordService.getTrend(...)         → C 做评估报告汇总时需要（也可能是 B 自己的趋势图用）

## C 提供给 B 的只读接口
- [ ] WarningService.countPendingByDoctor(...)   → B 做 Dashboard 时需要
- [ ] FollowupService.countCompletedByDoctor(...) → B 做 Dashboard 时需要
```

### 实战建议

1. 在各自 Service 接口中，把"对外暴露"的方法和"内部使用"的方法用注释分开
2. 对外方法尽量简单：传基本类型参数，返回 Entity 或简单统计值
3. 不要让对方直接传复杂 QueryWrapper 进来

## 四、Git 工作流

### 分支策略

```
main ─────●────────────────●──────────
           \                /
feature/A-org-com ●──●──●──
                         \
feature/B-elderly   ●──●──●──
                              \
feature/C-warning    ●──●──●──●──
```

### 操作步骤（以 B 为例）

```bash
# 1. 拉最新代码
git checkout main
git pull origin main

# 2. 创建功能分支
git checkout -b feature/B-elderly-crud

# 3. 开发 → 提交（小步提交，不要攒一大堆）
git add backend/src/main/java/com/swjtu/smec/entity/Elderly.java
git commit -m "feat: 新增 Elderly 实体类"

# 4. 推送
git push origin feature/B-elderly-crud

# 5. 在 GitHub 上创建 PR → A review → merge
```

### 提交信息规范

```
feat: 新增老人档案增删改查
fix: 修复预警处理时状态未更新
refactor: 提取公共分页查询逻辑
docs: 更新接口文档
chore: 添加 EasyExcel 依赖
```

### 合并冲突预防

| 容易冲突的文件 | 解决方案 |
|---------------|---------|
| `pom.xml` | A 统一维护，B/C 有新增依赖先告知 A |
| `application.yml` | A 写第一版，其他人用注释标出自己的配置段 |
| Router `index.js` | 每个人的路由用注释隔开，避免编辑同一行 |
| `App.vue` | 骨架搭好后基本不动 |

## 五、开发顺序（MVP 冲刺）

### 第一阶段（基础设施 — A 先动，B/C 并行写文档）

```
A: 建表(sys_* + notification + community) → Spring Security + JWT → 登录/注册 API
B: 等待 A 完成 → 参考 A 的建表脚本，建 elderly/family_contact/health_record → 实体类
C: 等待 A 完成 → 建 warning_*/followup_*/assessment_*/device* → 实体类
```

### 第二阶段（P0 用例并行开发）

```
三人完全并行：
A: UC-COM-01(医生档案管理) + UC-COM-02(老人分配医生)
B: UC-DOC-02(老人档案CRUD) + UC-DOC-03(健康数据导入)
C: UC-DOC-05(预警处理) + UC-DOC-06(随访计划) + UC-DEV-01(设备台账)
```

### 第三阶段（联调 + P1 用例）

```
B: UC-DOC-01(Dashboard) → 需要 C 提供预警/随访统计接口
C: UC-DEV-02(设备监控) + UC-DEV-03(维修报废)
A: UC-ORG-01 + UC-COM-03(报表)
```

### 第四阶段（收尾）

```
集成测试 → Bug 修复 → 演示准备 → 文档完善
```

## 六、日常协作 Checklist

- [ ] 每日站会前 `git pull` 最新代码
- [ ] 开始写一个功能前，检查是否已有别人写好的 Service 可以用
- [ ] 需要别人提供接口时，先在群里提出（不要等写到了才发现没接口）
- [ ] 提交前本地跑通 `mvn compile`（后端）/ `npm run dev`（前端）
- [ ] 冲突了自己解不开 → 找 A 一起解决
- [ ] 每天至少 push 一次，不要把所有代码憋在本地
