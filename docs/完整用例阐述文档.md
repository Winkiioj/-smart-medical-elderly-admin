## UC-ORG-01：查看各社区统计报表

---

### 用例编号

UC-ORG-01

### 用例名称

查看各社区统计报表

### 参与者

- 主参与者：机构管理员（卫健委/平台最高管理者）

### 前置条件

1. 管理员已登录系统，身份为"机构管理员"角色
2. 系统中存在至少两个已接入的社区，且各社区有老人数据

### 后置条件

无（本用例为纯查询操作，不修改系统数据）

### 基本流程

1. 管理员登录后默认进入 Dashboard 首页
2. 系统展示全局数据总览卡片：
   - 全区接入社区数、全区老人总数、本月全区新增老人数
   - 全区设备在线率、本月全区预警总数、全区预警处理率、全区随访完成率
3. 管理员点击侧边栏"报表统计"菜单
4. 系统进入报表页面，默认展示"社区对比"视图
5. 系统以表格形式展示各社区指标：
   - 列：社区名称、老人数、本月新增、签约医生数、预警总数、预警处理率、随访完成率、设备在线率
   - 行：每个社区一行，默认按社区名称排序
   - 预警处理率低于 80% 的行以黄色高亮，低于 60% 的以红色高亮
6. 系统以图表形式辅助展示：
   - 各社区老人数量柱状图
   - 各社区预警处理率对比柱状图
   - 各社区随访完成率对比柱状图
7. 管理员支持按时间范围筛选（本月/近三月/近半年/本年）
8. 管理员点击某社区的表格行
9. 系统展开该社区的详细指标：老人年龄分布饼图、性别比例饼图、近 6 个月新增老人趋势折线图、近 6 个月预警趋势折线图
10. 管理员浏览完毕后完成本次查看

### 异常流程

- 4a. 系统中仅有一个已接入社区
  → 系统仍展示数据，但不显示"对比"类图表（如各社区柱状对比图），仅显示该社区的详细指标
- 5a. 某社区本月无任何数据（新接入尚未运营）
  → 该社区的指标列显示"---"或"暂无数据"，不高亮
- 7a. 筛选的时间范围内无任何数据
  → 系统提示"所选时间范围内暂无数据"，保留筛选条件，不切换视图

### 业务规则

1. 机构管理员能看到全区所有社区的数据，无数据权限限制
2. 预警处理率 = 已完成预警数 / 预警总数 × 100%
3. 随访完成率 = 已完成随访数 / 应完成随访数 × 100%
4. 设备在线率 = 在线设备数 / 设备总数 × 100%，维修中的设备不计入在线
5. 数据统计均为实时查询，不使用缓存（机构管理员视角需保证数据准确性）
6. 各社区指标每日自动计算并记录快照（用于趋势图展示）

### 涉及数据

| 操作 | 表                                            |
| ---- | --------------------------------------------- |
| 读   | elderly（按 community 分组聚合）              |
| 读   | sys_user（统计各社区医生数，role='社区医生'） |
| 读   | warning_record（统计预警总数和处理率）        |
| 读   | followup_plan（统计随访完成率）               |
| 读   | device（统计设备在线率）                      |

### 优先级

P1 — 机构管理员的核心用例，但属于查看类功能，在 MVP 阶段只需完成基本数字卡片+简单表格，图表增强可在后续迭代

### 备注

- 技术要点：多表 GROUP BY + JOIN 聚合查询，社区维度需要与 elderly.community 字段对齐
- 前端：ECharts 柱状图 + 条件高亮表格
- 待确认：是否需要"点击某社区下钻查看该社区内各医生的指标对比"（可能作为 P2 扩展）

## UC-ORG-02：整理数据向上级汇报

---

### 用例编号

UC-ORG-02

### 用例名称

整理数据向上级汇报（导出报表）

### 参与者

- 主参与者：机构管理员

### 前置条件

1. 管理员已登录系统，身份为"机构管理员"角色
2. 管理员当前在"报表统计"页面（UC-ORG-01 的结果页）

### 后置条件

1. 浏览器下载了一份 Excel 文件（.xlsx）
2. 系统记录了导出操作日志

### 基本流程

1. 管理员在报表统计页面，已通过筛选条件确定了要汇报的数据视图
2. 管理员点击页面上的"导出 Excel"按钮
3. 系统弹出导出确认框，包含：
   - 当前筛选条件摘要（时间范围、数据类型）
   - 导出内容勾选：☑ 社区对比汇总表 ☑ 各社区详细指标 ☐ 老人基础数据明细 ☐ 预警记录明细
4. 管理员勾选需要的导出内容 → 点击"确认导出"
5. 系统在后端生成 Excel 文件，包含：
   - Sheet1"社区对比汇总"：与 UC-ORG-01 步骤5 的表格一致
   - Sheet2"各社区详情"：展开每个社区的年龄分布、性别比例、趋势数据（以文字+数据表形式，非图表）
   - （若勾选）Sheet3"老人明细"：全区老人基础信息列表
   - （若勾选）Sheet4"预警明细"：全区预警记录列表
6. 系统返回文件流，浏览器自动下载文件
7. 文件名格式：`智慧医养管理平台_报表_20260715_143200.xlsx`（含导出时间戳）
8. 管理员打开文件核对数据无误 → 将其作为向上级卫健委月报的附件

### 异常流程

- 3a. 管理员在未设置任何筛选条件的情况下点击导出
  → 系统默认导出"本月+全区"范围的数据，并在确认框中提示"当前为默认范围：本月全区数据"
- 5a. 所选时间范围内数据量为零
  → 系统提示"所选范围无数据，请调整筛选条件"，不生成文件
- 5b. 导出的数据量过大（如全区全年明细超过 10000 行）
  → 系统提示"数据量较大（预估XX行），导出可能需要 10-30 秒，是否继续？"
  → 管理员确认后执行导出，系统显示进度条
- 5c. 后端生成 Excel 时发生异常（如磁盘空间不足）
  → 系统提示"导出失败，请联系系统管理员"，记录错误日志

### 业务规则

1. 导出的 Excel 文件需包含表头行（中文）、数据行、导出时间、导出人
2. Excel 第一行为标题："智慧医养大数据公共服务平台 — 数据报表"
3. Excel 第二行为筛选条件说明："时间范围：2026年7月 | 范围：全区"
4. 数字列保留合理精度（百分比保留一位小数，如"85.3%"）
5. 导出操作记录日志（导出人、导出时间、筛选条件、导出数据量），但不需要在前端展示

### 涉及数据

| 操作 | 表                                                           |
| ---- | ------------------------------------------------------------ |
| 读   | 与 UC-ORG-01 相同（elderly, sys_user, warning_record, followup_plan, device） |
| 写   | 操作日志表（如有）                                           |

### 优先级

P1 — 汇报是关键场景，但 Excel 导出可在 MVP 第二阶段完成，第一阶段可先保证页面数据展示完整

### 备注

- 技术选型：EasyExcel（阿里开源，流式写入，支持大数据量）或 Apache POI
- 前端：axios 设置 responseType: 'blob'，接收文件流后触发下载
- 简化方案：如果 EasyExcel 集成有困难，可降级为 CSV 导出（牺牲多 Sheet 和格式）

## UC-COM-01：管理医生档案

---

### 用例编号

UC-COM-01

### 用例名称

管理本社区医生档案

### 参与者

- 主参与者：社区管理员

### 前置条件

1. 社区管理员已登录系统，身份为"社区管理员"角色
2. 社区管理员的数据权限仅限于其所属社区
3. 系统已存在至少一个角色（"社区医生"），用于分配

### 后置条件

1. 医生的系统账号已创建/更新/禁用
2. 操作结果记录在 sys_user 表中
3. （若是新增）系统向新医生发送账号激活通知

### 基本流程 — 查询医生列表

1. 管理员点击侧边栏"医生管理"菜单
2. 系统展示该管理员所属社区下的医生列表
3. 每条医生记录显示：姓名、手机号、性别、签约老人数、账号状态（启用/禁用）、入职日期
4. 管理员支持按姓名、手机号、账号状态进行搜索筛选
5. 列表默认按入职日期倒序排列，支持分页

### 基本流程 — 新增医生

6. 管理员点击"新增医生"按钮
7. 系统弹出新增医生表单
8. 管理员填写：
   - 必填项：姓名、手机号、性别、入职日期
   - 选填项：邮箱、备注
9. 管理员点击"保存"
10. 系统执行以下操作：
    - 校验手机号是否已被注册（sys_user 表）
    - 在校验通过后，自动生成用户名（手机号）和初始密码（随机6位或123456，首次登录强制修改）
    - 在 sys_user 表中创建一条记录，角色默认设为"社区医生"
    - 将该医生关联到当前管理员的社区
11. 系统提示"医生账号已创建"，展示初始用户名和密码（支持一键复制）
12. 管理员将初始密码告知医生，医生即可登录系统

### 基本流程 — 编辑医生信息

13. 管理员在列表中点击某医生的"编辑"按钮
14. 系统弹出编辑表单，回填当前信息（手机号不可修改，若需修改由机构管理员操作）
15. 管理员修改姓名、邮箱、备注等信息 → 点击"保存"
16. 系统更新 sys_user 表对应记录

### 基本流程 — 禁用/启用医生账号

17. 管理员在列表中点击某医生的"禁用"开关
18. 系统弹出确认框："确认禁用李医生的账号？禁用后该医生将无法登录系统，其签约老人需重新分配给其他医生。"
19. 管理员确认 → 系统将 sys_user.status 设为 0（禁用）
20. 系统将该医生名下所有未处理的预警标记为"已关闭"（关闭原因：医生账号已禁用）
21. 系统将该医生名下的签约老人（elderly.doctor_id）标记为"待重新分配"
22. 禁用后可重新启用，恢复后老人分配关系不变

### 异常流程

- 9a. 手机号已被注册（无论是否为本社区）
  → 系统提示"该手机号已存在，请核实后重试"，阻止保存
- 9b. 必填项为空
  → 系统标红提示"请填写XXX"，阻止保存
- 9c. 手机号格式不正确（非11位数字或以非1开头）
  → 系统提示"请输入正确的手机号码"
- 17a. 禁用时该医生名下有待处理的预警
  → 系统在确认框中额外提示"该医生当前有待处理预警 XX 条，禁用后将自动关闭"，管理员确认后执行

### 业务规则

1. 社区管理员只能管理自己社区的医生，不能查看或操作其他社区的医生
2. 用户名自动取手机号，初始密码随机生成或统一设为 123456
3. 医生账号默认分配"社区医生"角色，社区管理员不能分配其他角色
4. 禁用医生时，自动处理该医生的预警和签约老人
5. 手机号作为唯一标识，修改需由机构管理员操作（社区管理员无权修改手机号）
6. 系统记录医生的创建人（create_by）和创建时间

### 涉及数据

| 操作  | 表                                         |
| ----- | ------------------------------------------ |
| 读    | sys_user（查询本社区医生列表）             |
| 写    | sys_user（新增/更新/禁用）                 |
| 写    | sys_user_role（插入用户-角色关联）         |
| 读/写 | elderly（禁用医生时更新签约医生字段）      |
| 读/写 | warning_record（禁用医生时关闭待处理预警） |

### 优先级

P0 — 社区管理员的核心用例，医生必须先有账号才能登录系统操作

### 备注

- 技术要点：BCrypt 密码加密存储；SysUser 表加 community 字段标识所属社区
- 安全注意：初始密码生成后仅在创建成功时展示一次，不存明文日志
- 关联：本用例创建的医生账号，将在 UC-COM-02 中被用于分配老人

## UC-COM-02：为新入住老人分配签约医生

---

### 用例编号

UC-COM-02

### 用例名称

为新入住老人分配签约医生

### 参与者

- 主参与者：社区管理员

### 前置条件

1. 社区管理员已登录系统，身份为"社区管理员"角色
2. 该社区下存在至少一位状态为"启用"的社区医生
3. 系统中存在 doctor_id 为空（未分配医生）的老人记录

### 后置条件

1. 老人的签约医生已更新（elderly.doctor_id 已赋值）
2. 系统发送消息通知被分配的医生："您有新的签约老人，请及时查看档案"

### 基本流程

1. 管理员点击侧边栏"老人分配"菜单
2. 系统进入老人分配页面，默认展示"待分配老人"标签页
3. 系统列出该社区下所有 doctor_id 为空的老人，显示：
   - 老人姓名、性别、年龄、身份证号（脱敏，只显示后4位）、住址、入档日期
   - 按入档日期倒序排列（最新入住的排最前）
4. 每条老人记录右侧有一个"分配医生"下拉选择器
5. 管理员可为老人逐个分配，也可勾选多条老人后批量分配
6. 下拉选择器列出该社区所有启用状态的医生，每条显示：
   - 医生姓名 + 当前签约老人数
   - 签约数超过 200 的医生标记橙色（负荷偏高），超过 300 的标记红色（负荷过高）
7. 管理员根据医生负荷选择合适的人 → 点击"确认分配"
8. 系统校验该医生当前签约数是否已超上限（如 300 人）
9. 校验通过 → 系统更新 elderly.doctor_id
10. 该老人记录从"待分配"列表中移除，出现在"已分配"标签页
11. 系统自动向被分配的医生推送消息："您有新的签约老人：XXX，请登录系统查看档案"

### 基本流程 — 查看已分配老人

12. 管理员点击"已分配"标签页
13. 系统列出该社区下已分配医生的老人，显示老人姓名、签约医生、入档日期
14. 管理员可按医生筛选，"查看某医生名下的所有老人"
15. 管理员可点击"调整分配"按钮，弹出确认框后重新选择医生
16. 系统更新 elderly.doctor_id，并向新旧两位医生分别推送通知

### 基本流程 — 查看医生负荷

17. 管理员点击"医生负荷"标签页
18. 系统以表格展示该社区各医生负荷：
    - 医生姓名、当前签约数、本月新增数、本月预警处理率、本月随访完成率
    - 按签约数降序排列
19. 管理员据此判断哪位医生有富余精力接收新老人

### 异常流程

- 3a. 该社区下所有老人均已分配医生
  → 系统展示"暂无待分配老人"，提示管理员可通过老人档案模块新增老人
- 8a. 所选医生签约数已达上限
  → 系统提示"该医生当前签约数已达上限（300人），无法继续分配，请选择其他医生"
  → 分配操作被阻止
- 8b. 所选医生账号已被禁用
  → 系统不应展示被禁用的医生在下拉列表中（由前置过滤保证）
- 15a. 调整分配时，老人名下有未完成的预警
  → 系统提示"该老人当前有待处理预警，建议处理完成后再调整，是否继续？"
  → 管理员确认后执行调整，预警处理人同步更新为新医生
- 5a. 批量分配时，所选老人中部分已有医生
  → 系统过滤掉已有医生的老人，只分配无医生的，完成后提示"已分配 X 位，跳过 Y 位（已分配医生）"

### 业务规则

1. 社区管理员只能为所属社区的老人分配本社区内的医生
2. 每位医生签约上限 300 人（可配置），超出后不允许新分配
3. 调整分配（变更签约医生）后，原医生失去对该老人的数据访问权限，新医生获得访问权限
4. 分配/调整操作需向被分配医生推送消息通知
5. 医生禁用时，其名下的签约老人自动回到"待分配"状态

### 涉及数据

| 操作 | 表                                           |
| ---- | -------------------------------------------- |
| 读   | elderly（查询待分配老人 + 各医生签约数统计） |
| 读   | sys_user（查询社区医生列表及状态）           |
| 写   | elderly（更新 doctor_id）                    |
| 写   | notification（推送分配通知）                 |

### 优先级

P0 — 老人必须先分配到医生，医生才能看到老人并进行后续所有操作

### 备注

- 技术要点：elderly.doctor_id 更新后，前端需联动更新预警记录的处理人过滤逻辑
- 医生的"当前签约数"通过 `SELECT COUNT(*) FROM elderly WHERE doctor_id = ? AND is_deleted = 0` 实时统计
- 待确认：签约上限 300 是否合理（实际场景中一个医生管 200-300 位老人是比较常见的）

## UC-COM-03：查看本社区报表并导出

---

### 用例编号

UC-COM-03

### 用例名称

查看本社区报表并导出

### 参与者

- 主参与者：社区管理员

### 前置条件

1. 社区管理员已登录系统，身份为"社区管理员"角色
2. 该社区已有老人数据和运营数据

### 后置条件

无（若导出则浏览器下载 Excel 文件）

### 基本流程

1. 管理员登录后默认进入 Dashboard 首页
2. 系统展示该管理员所属社区的数据总览卡片：
   - 本社区老人总数、本月新增老人数、签约医生数
   - 设备在线率、本月预警总数、预警处理率、随访完成率
3. 系统展示辅助图表：
   - 本社区老人年龄分布饼图
   - 本社区近 30 天新增老人趋势折线图
   - 各医生随访完成率对比柱状图
   - 本月预警记录列表（前 5 条，红色高亮待处理的）
4. 管理员支持切换时间范围（本月/近三月/近半年/本年）以更新所有数据
5. 管理员点击侧边栏"报表统计"菜单
6. 系统进入报表详情页，包含以下分区：
   - **老人统计区：** 按年龄段分布饼图、性别比例饼图、近 6 个月新增趋势折线图、各医生签约老人数柱状图
   - **预警统计区：** 按预警级别（轻度/中度/重度）分布饼图、按预警类型占比饼图、近 6 个月预警趋势折线图、预警处理率趋势
   - **随访统计区：** 各医生随访完成率对比柱状图、随访方式分布饼图（电话/上门/门诊）、本月随访逾期率
   - **设备统计区：** 设备类型分布、设备在线率、近 6 个月设备告警趋势
7. 管理员浏览报表，确认数据无误
8. 管理员点击"导出 Excel"按钮
9. 系统弹出导出确认框：摘要当前筛选条件、勾选导出分区
10. 管理员勾选需要的分区 → 点击"确认导出"
11. 系统生成 Excel 文件并触发浏览器下载
12. 文件名格式：`智慧医养管理平台_XX社区报表_20260715.pdf`
13. 管理员用导出的文件作为向上级（机构管理员/卫健委）汇报的材料

### 异常流程

- 2a. 该社区本月无任何运营数据（新接入社区）
  → 数字卡片显示 0，图表显示"暂无数据"
- 6a. 某分区数据为空（如本月无任何预警）
  → 该分区显示"本月暂无预警数据"，不展示空图表
- 10a. 导出时数据量为零
  → 系统提示"所选范围无数据，无法导出"，不生成文件
- 11a. 导出过程异常
  → 系统提示"导出失败，请重试"，记录错误日志

### 业务规则

1. 社区管理员只能查看本社区的数据，不能查看其他社区或全区汇总数据
2. 所有统计指标的聚合维度均为本社区
3. 医生维度的对比（如各医生随访完成率）仅包含本社区内的医生
4. 报表数据实时查询，不使用缓存（保证准确性）
5. 导出 Excel 格式标准与 UC-ORG-02 保持一致

| ---- | ------------------------------------------------------------ |

## 用例阐述

### 用例编号：UC-DOC-01

### 用例名称

查看个人 Dashboard

### 参与者

- 主参与者：社区医生

### 前置条件

1. 医生已登录系统，身份为"社区医生"
2. 医生名下存在签约老人（数据为空时也允许进入，各卡片显示为 0）

### 后置条件

1. Dashboard 聚合数据在页面正确展示
2. （本用例为纯查询操作，无持久化状态变更）

### 基本流程

1. 医生登录系统，系统校验 JWT Token 和 RBAC 权限后，默认跳转至 Dashboard 首页
2. 系统从 Redis 缓存读取该医生的 Dashboard 聚合数据
3. 系统展示顶部数字卡片行，包含：
   - 负责老人总数
   - 本月新增老人数
   - 签约老人设备在线率
   - 待处理预警数（红色角标标注）
   - 未读消息数（红色角标标注）
4. 医生点击任意数字卡片，系统跳转至对应的功能页面（如点击"待处理预警数"→ 跳转预警列表）
5. 系统展示中间图表区：
   - 近 30 天新增老人趋势折线图
   - 签约老人年龄分布饼图
6. 系统展示底部预警区：最新预警记录列表（前 5 条），按级别着色（重度红色、中度黄色、轻度绿色），待处理项高亮
7. 医生可点击某条预警记录，系统跳转至该预警详情页

### 异常流程

- 2a. Redis 缓存不存在或已失效 → 系统从数据库实时查询聚合数据，查询完成后回写 Redis 缓存
- 2b. 数据库查询超时或异常 → 系统提示"数据加载中，请稍后刷新页面重试"，各卡片显示为"--"
- 3a. 医生名下暂无签约老人 → 数字卡片全部显示 0，图表区展示空状态占位图，提示"暂无数据"
- 3b. 设备在线率计算时无设备数据 → 在线率显示"--"，不显示错误

### 业务规则

1. Dashboard 聚合数据默认从 Redis 缓存读取，缓存过期时间 30 分钟
2. 待处理预警数和未读消息数通过 COUNT 实时查询，不走缓存
3. 所有数据仅统计当前登录医生签约的老人范围，其他医生的数据不可见（数据权限）
4. 数字卡片按从左到右优先级排列：待处理预警数 > 负责老人数 > 未读消息数 > 本月新增 > 设备在线率
5. 预警列表前 5 条按级别（重度 > 中度 > 轻度）和触发时间（倒序）双重排序

### 涉及数据

| 操作 | 表             |
| ---- | -------------- |
| 读   | elderly        |
| 读   | warning_record |
| 读   | health_record  |
| 读   | followup_plan  |
| 读   | notification   |
| 读   | device         |
| 写   | （无）         |

### 优先级

P0 — MVP 必须完成，Dashboard 是医生登录后的第一入口

### 备注

- 技术要点：聚合查询涉及多表 JOIN + COUNT + GROUP BY，需注意 SQL 性能，建议对 elderly.doctor_id、warning_record.status 建立联合索引
- 前端图表使用 ECharts 渲染：折线图（新增趋势）和饼图（年龄分布）
- 待确认：Dashboard 数据是进入页面时一次性加载，还是各卡片独立异步加载

### 用例编号：UC-DOC-02

### 用例名称

新增/编辑/查询老人档案

### 参与者

- 主参与者：社区医生
- 辅助参与者：系统（身份证号自动解析）

### 前置条件

1. 医生已登录系统，身份为"社区医生"
2. 系统中存在已配置的社区列表和签约医生列表（供下拉选择）

### 后置条件

1. （新增）老人档案记录已写入 elderly 表，家属信息已写入 family_contact 表
2. （编辑）老人档案信息已更新
3. （新增/编辑）系统生成操作日志，记录操作人、操作时间、操作类型
4. （新增）系统推送建档通知消息给签约医生
5. （查询）无持久化状态变更

### 基本流程

1. 医生点击侧边栏"老人档案"菜单
2. 系统展示老人档案列表页，顶部提供筛选条件栏（姓名、身份证号、所属社区、年龄段），下方为分页表格
3. 表格每行展示：姓名、性别、年龄、身份证号（脱敏）、所属社区、签约医生、入档日期、操作按钮（查看/编辑）
   - 3a. 新增子流程
4. 医生点击列表页"新增老人"按钮
5. 系统展示新增老人表单页，包含：
   - 基本信息区：姓名*、身份证号*、联系电话、住址、所属社区*（下拉）、签约医生*（下拉）、入档日期（默认当天）
   - 家属信息区：可动态添加多行（姓名、关系、手机号、是否紧急联系人）+ [添加家属] 按钮
6. 医生填写基本信息，输入身份证号后按 Tab 或失焦
7. 系统自动从身份证号解析出生日期和性别，回填对应字段（字段置灰不可手动编辑）
8. 医生点击"添加家属"，系统新增一行家属信息输入框
9. 医生填写家属姓名、关系（下拉：配偶/子女/父母/兄弟姐妹/其他）、手机号，勾选是否紧急联系人
10. 医生点击"保存"
11. 系统进行前端表单校验：
    - 姓名和身份证号不能为空
    - 身份证号格式 18 位（末位可为 X）
    - 手机号格式 11 位数字
    - 所属社区和签约医生已选择
12. 系统校验身份证号唯一性：查询 elderly 表是否存在同号记录
13. 系统在同一个数据库事务中写入 elderly 表和 family_contact 表
14. 系统发送建档通知消息给签约医生
15. 页面跳转回老人列表页，新记录出现在第一条，列表自动刷新
    - 3b. 编辑子流程
16. 医生在老人列表页点击某条记录的"编辑"按钮
17. 系统展示编辑表单页，回填所有现有数据（含已有家属信息列表）
18. 医生修改信息后点击"保存"
19. 系统校验并更新 elderly 表和 family_contact 表（先删后插家属记录，同一事务）
20. 页面跳转回列表页，提示"修改成功"
    - 3c. 查询子流程
21. 医生在筛选栏输入关键词或选择筛选条件
22. 系统根据条件模糊匹配（姓名、身份证号支持模糊搜索），组合社区下拉和年龄段范围筛选
23. 系统展示筛选后的分页列表结果

### 异常流程

- 11a. 姓名或身份证号为空 → 系统标红必填字段，按钮置灰，提示"请填写必填信息"
- 11b. 身份证号格式不正确（非18位或含非法字符）→ 系统提示"请输入正确的18位身份证号"
- 11c. 手机号格式不正确 → 系统提示"请输入正确的11位手机号"
- 11d. 所属社区或签约医生未选择 → 系统标红下拉框，提示"请选择"
- 12a. 身份证号已存在 → 系统弹窗提示"该身份证号已存在（姓名：XXX），请检查是否重复建档"，不提交表单
- 13a. 数据库事务写入失败 → 系统回滚事务，提示"保存失败，请稍后重试"
- 16a. 医生试图编辑不属于自己签约的老人 → 系统提示"无权限编辑该老人档案"（按钮应置灰或隐藏）
- 18a. 编辑过程中其他用户已删除该老人 → 保存时系统提示"该档案已被删除"，刷新列表
- 21a. 筛选结果为空 → 系统展示空状态占位图，提示"未找到匹配的老人档案，请调整筛选条件"
- 22a. 网络超时 → 系统提示"网络异常，请检查网络后重试"

### 业务规则

1. 身份证号全国唯一，重复则阻止新增（编辑时若未修改身份证号则不触发唯一性校验）
2. 出生日期从身份证号第 7-14 位自动提取（格式 YYYY-MM-DD），性别从第 17 位判定（奇数=男，偶数=女），解析后字段不可手动修改
3. elderly 表与 family_contact 表在同一数据库事务中写入（@Transactional），编辑时家属记录采用"先删后插"策略
4. 签约医生下拉列表仅显示角色为"社区医生"且状态为"启用"的用户
5. 社区医生仅能查看和编辑自己签约的老人档案（数据权限），其他医生的老人不可见
6. 老人列表默认按入档日期倒序排列，分页大小 20 条/页
7. 家属联系人至少需要一个紧急联系人，但不强制

### 用例编号：UC-DOC-03

### 用例名称

导入老人健康数据

### 参与者

- 主参与者：社区医生

### 前置条件

1. 医生已登录系统，身份为"社区医生"
2. 医生本地存有一份已按标准格式整理好的当日老人健康检测数据文件（Excel .xlsx 或 CSV .csv）
3. 数据文件中包含的老人均在当前医生的签约范围内
4. 数据文件的列名和顺序与系统要求一致（身份证号、测量日期及各项健康指标）

### 后置条件

1. 文件中的健康记录已全部写入 health_record 表
2. 体重和身高均有值时，BMI 自动计算并写入
3. 写入的健康数据已触发预警规则扫描（超阈值则自动生成预警记录）
4. 页面提示"数据更新成功"，医生切换到 Dashboard 可看到最新数据

### 基本流程

1. 医生收到护工当日按标准格式整理好的老人健康检测数据文件
2. 医生点击左侧导航栏"健康管理 → 数据导入"
3. 系统展示数据导入页面：一个文件拖拽上传区域（也支持点击选择文件），接受 .xlsx / .csv 格式
4. 医生将文件拖入上传区域
5. 系统后台自动执行：
   - 校验文件格式和列名
   - 根据身份证号匹配 elderly 表中的老人
   - 跳过非当前医生签约老人的行
   - 体重和身高均不为空时自动计算 BMI
   - 逐条写入 health_record 表
   - 写入后自动触发预警规则扫描
6. 页面显示"数据更新成功"
7. 医生切换到 Dashboard 页面，可看到更新后的健康数据统计、预警列表等

### 异常流程

- 5a. 文件格式不是 .xlsx 或 .csv → 提示"仅支持 .xlsx 或 .csv 格式"
- 5b. 文件列名与系统要求不一致 → 提示"文件列名不匹配，缺少列：[XXX]"
- 5c. 文件中无可导入的有效数据行（全部跳过）→ 提示"数据更新成功（无新增数据）"
- 5d. 文件解析或数据库写入异常 → 提示"导入失败，请稍后重试"

### 业务规则

1. 医生只需拖入文件即可，系统自动完成解析、匹配、写入、预警触发全流程
2. 数据文件由护工按标准格式提前整理好，医生无需再手动处理
3. 身份证号是匹配老人的唯一标识，无法匹配的行跳过
4. 医生只能导入自己签约老人的数据（非签约老人跳过）
5. BMI = 体重(kg) / (身高(m))²，自动计算，保留一位小数
6. 同老人 + 同日期 + 同指标，后导入覆盖先导入
7. 24 小时内同老人 + 同指标类型不重复生成预警

### 涉及数据

7. 医生调整时间范围（如切换到"近 90 天"或自定义起止日期），系统重新查询并更新图表
8. 医生可在图表上拖拽缩放（ECharts dataZoom）查看某段区间的细节

1. 趋势图使用 ECharts 折线图渲染，每个数据点为一次测量记录
2. 图表 Y 轴默认展示正常参考范围（浅绿色背景区间），参考范围值取自预警规则表中该指标类型的默认阈值
3. 数据点按测量日期升序排列（从旧到新）
4. 同一测量日期有多条记录时，取最新录入的一条展示
5. 仅展示当前登录医生签约老人的数据（数据权限校验）
6. 图表支持 ECharts 交互：鼠标悬停 Tooltip、拖拽缩放（dataZoom）、图例点击显隐
7. 指标类型选择器按使用频率排列：血压（收缩压/舒张压）> 血糖 > 心率 > 血氧 > 体重 > BMI

| ---- | -------------------------------- |
| 读   | health_record                    |
| 读   | elderly                          |
| 读   | warning_rule（获取正常参考范围） |
| 写   | （无）                           |

### 优先级

P1 — 尽量完成，趋势图为医生判断健康走势提供直观依据，缺少时仍可通过列表数据人工判断，但体验明显降级

### 备注

- 技术要点：前端 ECharts 初始化后通过 AJAX 请求后端接口获取数据，接口需支持指标类型 + 时间范围参数，返回 JSON 数组（日期 + 数值）

## UC-DOC-05 处理预警

### 用例编号

UC-DOC-05

### 用例名称

处理预警

### 参与者

- 主参与者：社区医生

### 前置条件

1. 医生已登录系统，身份为"社区医生"角色
2. 系统中存在至少一条状态为"待处理"的预警记录
3. 该预警记录关联的老人档案状态为正常（未迁出）

### 后置条件

1. 预警记录状态已变更（处理中 / 已完成 / 已关闭）
2. 预警处理操作日志已生成（操作人、操作时间、操作类型）
3. 预警处理完成后，消息通知已推送给老人紧急联系人和社区管理员

### 基本流程

1. 医生点击左侧导航栏"预警管理 → 预警记录"
2. 系统展示预警列表，默认按状态排序（待处理优先），同状态按触发时间倒序
3. 医生点击某条"待处理"预警行
4. 系统展示预警详情，包含四个区域：预警基本信息（规则名称、触发时间、当前值、
   阈值、级别）、该老人近7天对应指标的趋势折线图、老人基本信息卡片（姓名、年龄、
   性别、既往病史、紧急联系人）、该预警的历史处理时间线
5. 医生查看数据后判断预警是否属实
6. 医生点击"接单处理"按钮
7. 系统将预警状态变更为"处理中"，记录接单人和接单时间
8. 医生通过电话或上门方式联系老人核实健康情况
9. 医生在"处理意见"文本框中填写核实情况，在"处理结果"下拉框中选择处理结果
10. 医生点击"完成处理"按钮
11. 系统校验必填项均已填写，将预警状态变更为"已完成"，记录处理意见、处理结果、
    完成时间
12. 系统向老人紧急联系人和所在社区管理员推送处理完成通知

### 异常流程

- 5a. 医生判定为误报 → 医生点击"关闭预警"，选择关闭原因并填写说明后确认，
  系统将状态变更为"已关闭"，记录关闭人、关闭时间、关闭原因
- 6b. 预警状态已变更为"已完成"或"已关闭" → 系统提示"该预警状态已变更"，刷新页面
- 6c. 预警关联的老人档案已被迁出 → 系统自动关闭预警，关闭原因记录为"老人已迁出"
- 9a. 处理意见超过 500 字 → 输入框阻止继续输入，提示"不超过 500 字"
- 10a. 未填写处理意见或未选择处理结果 → 前端校验提示"请填写必填项"
- 11a. 保存时数据库操作失败 → 系统提示"保存失败，请稍后重试"，状态不变

### 业务规则

1. 同一老人 + 同一预警指标类型，24 小时内不重复生成预警（已关闭的误报不参与去重）
2. 预警状态流转方向：待处理 → 处理中 → 已完成/已关闭，已完成和已关闭为终态，不可再变更
3. 预警级别判定：指标值超出阈值 ≥ 50% 为紧急，20%-50% 为重要，< 20% 为一般
4. 预警处理时效考核：预警生成到接单 ≤ 30 分钟为及时，30-120 分钟为一般，> 120 分钟为超时
5. 医生只能看到和处理自己签约老人的预警记录

### 涉及数据

| 操作 | 表                                                           |
| ---- | ------------------------------------------------------------ |
| 读   | warning_record, warning_rule, elderly, health_record, sys_user |
| 写   | warning_record（更新状态和处理信息）                         |
| 写   | warning_operation_log（操作日志）                            |
| 写   | notification（推送通知）                                     |

### 优先级

P0 — 预警处理是智慧医养系统的核心闭环，缺失则核心业务链路断裂

### 备注

- 技术难点：近7天趋势折线图需查询 health_record 表做日期聚合，前端用 ECharts 渲染并标注阈值参考线
- 待确认：预警通知是否同时发短信（MVP 阶段建议先做 App 内通知）
- 关联用例：依赖 UC-DOC-03（录入健康数据触发预警生成）、UC-COM-02（分配签约医生）

## UC-DOC-06 制定与执行随访计划

### 用例编号

UC-DOC-06

### 用例名称

制定与执行随访计划

### 参与者

- 主参与者：社区医生
- 辅助参与者：老人 / 老人家属（随访执行时的被访对象）

### 前置条件

1. 医生已登录系统，身份为"社区医生"角色
2. 目标老人档案已存在且未迁出
3. 目标老人与当前医生存在签约关系

### 后置条件

1. 随访计划已创建，初始状态为"待执行"
2. 若随访已执行，随访记录已保存，计划状态已更新为"已完成"
3. 若医生指定了下次随访日期，系统自动生成下次随访计划

### 基本流程

1. 医生点击左侧导航栏"随访管理 → 随访计划"
2. 系统展示随访计划列表，每条展示：计划编号、老人姓名、随访类型、计划日期、状态
3. 医生点击"新建随访计划"按钮
4. 系统弹出创建表单，包含：选择老人、随访类型、计划随访日期、随访方式、随访重点标签、备注
5. 医生选择目标老人（下拉搜索框，按姓名拼音排序）
6. 系统自动填充老人信息卡片，并在旁边展示该老人最近 3 次随访的日期和结论摘要
7. 医生选择随访类型、计划日期、随访方式后点击"保存"
8. 系统校验通过后保存随访计划，初始状态为"待执行"，计划编号自动生成
9. 到计划日期当天，医生在"今日待随访"列表中找到该计划，点击"开始随访"
10. 系统将计划状态变为"执行中"，展示随访表单
11. 医生逐项填写：健康指标（血压/血糖/心率/体重/体温）、用药情况、生活方式评估、
    心理筛查（PHQ-2，2题各0-3分）、随访结论
12. 系统自动计算心理筛查总分，若 ≥ 3 分在结论区展示"需关注心理健康"提示
13. 医生选择下次随访建议日期后，点击"完成随访"
14. 系统校验必填项，保存随访记录，将计划状态变更为"已完成"
15. 系统根据下次随访建议日期自动生成一条新的随访计划（状态="待执行"）

### 异常流程

- 8a. 同老人 + 同随访类型已存在"待执行"或"执行中"的计划 → 系统提示已有未完成计划，
  询问是否继续创建
- 10a. 计划日期已过医生仍未执行 → 列表行标记"逾期"（橙色），逾期超 7 天自动取消
- 11a. 输入的健康指标值明显异常（如收缩压 > 250）→ 弹出警告确认框，不阻止保存
- 11b. 心理筛查总分 ≥ 3 分 → 随访结论区自动追加"需关注心理健康"提示，
  下次随访建议间隔缩短
- 13a. 必填项未填写 → 前端高亮未填项，滚动到第一个未填位置
- 14a. 自动生成下次计划日期与已有计划冲突（同日同类型）→ 系统自动后移一天并备注

### 业务规则

1. 随访计划状态流转：待执行(0) → 执行中(1) → 已完成(2)；逾期 7 天自动取消(3)
2. 随访类型与默认间隔：常规 3 个月、慢病 1 个月、术后 2 周、产后 3-7 天首次、
   年度体检 1 年、临时随访无默认间隔
3. 医生只能查看和操作自己签约老人的随访计划
4. 随访中录入的健康指标（血压/血糖/心率）同步写入 health_record 表并触发预警规则扫描
5. 已完成的随访记录不允许修改健康数据，如需补充需创建临时随访计划

### 涉及数据

| 操作 | 表                                        |
| ---- | ----------------------------------------- |
| 读   | elderly, follow_up_plan, follow_up_record |
| 写   | follow_up_plan（创建/更新计划）           |
| 写   | follow_up_record（创建/更新随访记录）     |
| 写   | health_record（同步写入健康指标）         |
| 写   | warning_record（健康数据异常触发预警）    |

### 优先级

P0 — 随访管理是社区医生日常核心工作流，缺失则无法形成完整业务闭环

### 备注

- 技术要点：随访草稿自动暂存（前端 localStorage + 每 30 秒保存）；下次计划自动生成逻辑

UC-DOC-07

生成与填写健康评估报告

2. 目标老人档案已存在且为该医生的签约老人
3. 系统中预置了至少一份评估报告模板
4. 目标老人至少有 1 条健康数据记录（否则评估数据汇总区无数据可展示）

### 后置条件

1. 健康评估报告已保存，状态为"评估中"或"已完成"
2. 若已完成，评估总分和综合等级已生成
3. 评估报告 PDF 文件已生成并可下载/打印

### 基本流程

1. 医生点击左侧导航栏"评估管理 → 健康评估"
2. 系统展示评估报告列表，每条显示：老人姓名、评估模板名称、评估状态、综合等级、
   创建时间
3. 医生点击"新建评估报告"按钮
4. 系统弹出创建表单：选择老人、选择评估模板、备注（选填）
5. 医生选择老人和模板后，系统自动拉取并预填充基础信息区：老人基本信息、
   近 30 天健康数据汇总（血压/血糖/心率/BMI）、近 30 天预警汇总、最近 3 次随访摘要
6. 医生确认数据无误后点击"开始评估"
7. 系统保存评估记录（状态="评估中"），切换到评估表单页
8. 评估表单按模板中的评分维度逐项展示，每个维度包含题目、选项和分值说明
9. 医生逐维度勾选评分项（ADL 日常生活能力、MMSE 认知功能、MNA-SF 营养状况、
   Morse 跌倒风险、NRS 疼痛评估、GDS-15 抑郁筛查、社会支持评估），
   每项选择后实时显示该项得分，每个维度完成后自动计算合计分
10. 医生完成全部评分项后点击"查看评估结果"
11. 系统自动计算各维度得分和等级、综合总分和综合等级（优秀/良好/一般/需改善/差），
    展示结果预览页（雷达图 + 各维度明细表 + 高风险项列表）
12. 医生在结果预览页填写"评估结论"（不少于 20 字）和"健康建议"
13. 医生点击"完成评估"
14. 系统校验必填项通过后，将评估状态变更为"已完成"，生成 PDF 文件，记录完成时间

### 异常流程

- 5a. 老人无健康数据记录 → 系统提示"无健康数据，评估结果可能不完整，是否继续？"
- 5b. 自动拉取数据失败 → 健康汇总区显示"加载失败"，提供"重新加载"按钮
- 8a. 评分过程中途退出 → 系统自动暂存当前评分进度，重新进入时恢复
- 12a. 评估结论不足 20 字 → 前端提示"评估结论至少 20 字，当前 X 字"
- 14a. PDF 生成失败 → 提示"PDF 生成失败，请稍后重试"，数据和结论不受影响，
  提供"重新生成 PDF"按钮
- 14b. 完成后发现评分有误 → 不允许直接修改，需点击"创建修订版本"基于原报告修改

### 业务规则

1. 综合等级判定：≥ 90% 优秀，75-89% 良好，60-74% 一般，40-59% 需改善，< 40% 差
2. 同老人 + 同评估模板，一个月内只允许创建一次，修改走修订版本流程
3. 各维度权重由模板预设，医生不可在评估过程中修改权重
4. PDF 命名格式：`评估报告_老人姓名_模板名称_完成日期.pdf`
5. 医生只能评估自己签约的老人

| 读   | assessment_template（评估模板和评分规则）                |
| 读   | assessment_record（历史评估报告，用于趋势对比）          |
| 写   | assessment_record（创建/更新评估报告）                   |

P1 — 尽量完成，评估报告是增值功能，MVP 阶段缺失不阻断核心业务流程

### 备注

- 技术要点：评估模板用 JSON 存储在 assessment_template 表中；雷达图用 ECharts；

1. 报修请求已提交，状态为"待处理"
2. 报修记录对设备管理员可见（出现在维修请求列表中）

### 基本流程

1. 医生在出诊或入户随访过程中发现携带的社区公用设备出现异常
   （如腕表无法开机、血压计读数明显偏差、设备外观损坏），
   可通过两种路径进入报修：
   - 路径一：在随访工作台或出诊记录页面点击"设备报修"按钮
   - 路径二：左侧导航栏"设备管理 → 设备报修"，手动选择设备
2. 系统弹出报修表单，自动填充：设备编号、设备名称、设备类型、报修医生姓名和所属社区
3. 医生填写以下报修信息：
   - 故障类型（下拉选择，必填）：设备无法开机 / 数据明显异常 / 外观损坏 /
     电池续航严重下降 / 设备遗失 / 其他
   - 故障描述（文本域，必填，不超过 500 字）
   - 发现时间（日期时间选择器，默认当前时间，必填）
   - 紧急程度（单选，必填）：普通（社区仍有同类型备用设备）/
     紧急（该类型设备紧缺，影响社区日常出诊工作）
4. 医生点击"提交报修"
5. 系统校验必填项通过后，保存报修记录，状态为"待处理"，生成报修编号
6. 系统向设备管理员推送报修通知（消息列表 + Dashboard 待办数 +1），
   同时在设备台账中标记该设备为"报修中"
7. 设备管理员处理报修后（受理或拒绝），系统向报修医生推送处理结果通知
8. 医生可在"设备报修"页面查看已提交报修的处理进度

### 异常流程

- 3a. 故障描述超过 500 字 → 输入框阻止继续输入，提示"不超过 500 字"
- 4a. 必填项未填写 → 前端高亮未填项，提示"请填写必填项"
- 4b. 同一设备已存在"待处理"的报修记录 → 系统提示"该设备已有待处理的报修记录
  （报修编号 XXX），确认是否仍要提交？"
- 4c. 保存时数据库操作失败 → 提示"提交失败，请稍后重试"
- 7a. 设备管理员拒绝报修 → 医生收到通知，可查看拒绝原因，报修状态变更为"已拒绝"

### 业务规则

1. 报修状态流转：待处理(0) → 已受理(1) → 已完成(2)；待处理(0) → 已拒绝(3)
2. 该社区的医生均可为社区公用设备提交报修
3. 同一设备可多次报修，但前一次报修状态为"待处理"或"已受理"时不建议重复提交
4. 紧急报修提交后，系统额外向设备管理员发送一条高优先级消息
5. 报修编号规则：`RP-YYYYMMDD-序号3位`

### 涉及数据

| 操作 | 表                                    |
| ---- | ------------------------------------- |
| 读   | device（查询设备信息）                |
| 写   | device_repair_request（创建报修记录） |
| 写   | notification（推送通知给设备管理员）  |

### 优先级

P1 — 报修是医生发现设备问题后的标准反馈通道，完善设备管理闭环

### 备注

- 技术要点：报修提交后需实时推送通知给设备管理员（WebSocket 或轮询）；
  设备台账详情页需展示设备当前报修状态
- 待确认：报修的故障类型枚举是否需要在后续版本扩展
- 关联用例：本用例为 UC-DEV-03（设备状态管理）提供报修来源；
  设备管理员处理报修后，医生可通过本用例的报修列表查看处理进度

## UC-DEV-02 查看设备在线状态并处理离线告警

### 用例编号

UC-DEV-02

### 用例名称

查看设备在线状态并处理离线告警

### 参与者

- 主参与者：设备管理员

### 前置条件

1. 设备管理员已登录系统，身份为"设备管理员"角色
2. 系统中存在至少 1 台已录入的设备台账记录
3. IoT 设备后台服务正常运行

### 后置条件

1. 设备状态面板已刷新显示最新设备在线/离线状态
2. 离线设备的告警记录已生成并可供处理
3. 离线告警处理结果已记录

### 基本流程

1. 设备管理员点击左侧导航栏"设备管理 → 设备监控"
2. 系统展示设备监控页：顶部 4 个数字卡片（总数/在线/离线/异常）+ 状态分布饼图；
   下方设备实时监控列表（默认每 30 秒自动刷新）
3. 列表每条显示：设备编号和名称、设备类型、所属社区、在线状态指示灯（绿/黄/红/灰）、
   最近心跳时间、离线累计时长
4. 系统检测到某设备心跳超 30 分钟无更新，自动将其状态标记为"离线"（红色），
   生成一条离线告警记录，同时向设备管理员推送 WebSocket 实时通知
5. 设备管理员点击该离线设备行进入详情页
6. 系统展示设备运行详情：当前状态和离线持续时间、心跳历史时间线（最近 24 小时）、
   关联的离线告警记录列表
7. 设备管理员判断离线原因后，点击"处理离线告警"按钮
8. 系统弹出处理对话框：选择处理方式（已确认设备正常-关闭告警 / 电池耗尽 /
   设备闲置未使用 / 硬件故障-提交维修 / 网络信号问题-待观察 / 其他）、
   填写处理说明
9. 设备管理员选择处理方式并填写说明后，点击"确认处理"
10. 系统根据处理方式更新告警状态（已关闭 / 处理中），记录处理日志

### 异常流程

- 4a. IoT 后台服务故障导致所有设备心跳数据异常 → 页面顶部展示红色横幅提示
  "设备数据接收服务异常"，不生成离线告警
- 4b. 设备 1 小时内状态切换 ≥ 5 次 → 该设备行标记"信号不稳定"（橙色），
  同设备同天内最多生成 2 条离线告警
- 5a. 设备离线超 24 小时 → 自动提升预警级别至"紧急"，
  加急推送给设备管理员
- 8a. 设备管理员处理过程中设备恢复上线 → 对话框顶部提示"设备已重新上线"，
  对应的离线告警自动关闭

### 业务规则

1. 设备心跳判定：最近心跳 ≤ 5 分钟=在线，5-30 分钟=延迟，> 30 分钟=离线
2. 离线告警级别：30-120 分钟=一般，120-360 分钟=重要，> 360 分钟=紧急
3. 去重规则：同设备同一天最多生成 2 条离线告警
4. 设备列表默认 30 秒自动刷新一次，管理员可手动刷新
5. 设备管理员只能看到自己管理范围内的设备

| 读   | warning_record（关联的离线告警）         |
| 写   | warning_record（生成或更新离线告警）     |
| 写   | device_operation_log（告警处理操作日志） |
| 写   | notification（推送告警消息）             |

P1 — 尽量完成，设备监控是运维核心功能，14 天内 IoT 数据模拟需提前准备

- 技术要点：后台定时任务（@Scheduled）每分钟扫描设备心跳；WebSocket 实时推送；

- 待确认：离线判定阈值是否合理；是否需要非工作时间的短信通知

## UC-DEV-03 更新设备状态（维修与报废）

### 用例编号

UC-DEV-03

### 用例名称

更新设备状态（维修与报废）

### 参与者

- 主参与者：设备管理员

### 前置条件

1. 设备管理员已登录系统，身份为"设备管理员"角色
2. 目标设备台账记录已存在
3. 目标设备当前状态不为"已报废"（报废为终态）

### 后置条件

1. 设备状态已按指定方向流转（维修中 / 已修复 / 已报废）
2. 设备状态变更日志已记录
3. 若维修来源为医生报修，对应报修记录状态已同步更新

### 基本流程

1. 设备管理员可通过以下途径进入设备状态管理：
   - 途径一（主动巡检）：在台账列表中点击目标设备行的"状态管理"按钮
   - 途径二（处理报修）：左侧导航栏"设备管理 → 维修请求"，
     查看医生提交的设备报修列表
2. 若从途径二进入，系统展示维修请求列表，每条显示：报修编号、设备编号和名称、
   报修医生姓名、所属社区、故障类型、紧急程度标签、提交时间、处理状态
3. 设备管理员可按处理状态（待处理/已受理/已完成/已拒绝）、紧急程度筛选
4. 设备管理员点击某条"待处理"报修记录，进入报修详情页
5. 系统展示：报修基本信息（故障类型、故障描述、发现时间、紧急程度）、
   设备摘要（编号、名称、类型、当前状态、所属社区）、设备近期运行数据（心跳历史、
   最近 24 小时数据上报量，帮助判断故障原因）
6. 设备管理员核实后点击"受理维修"按钮
7. 系统弹出状态变更对话框，展示设备摘要，自动勾选维修原因为"医生报修"，
   关联报修编号自动填充
8. 若设备管理员直接从途径一（台账列表）进入，手动选择目标状态
9. 若选择"维修中"：系统展示维修信息表单，维修原因选项包含：
   - 医生报修（若有已关联的报修记录则自动选中并显示报修编号和故障描述摘要）
   - 设备硬件故障
   - 设备进水
   - 设备外观损坏
   - 例行保养与校准
   - 设备离线告警触发的维修（来自 UC-DEV-02）
   - 其他（需填写说明）
   - 维修方式（返厂/现场/第三方）、预计天数、维修说明
10. 若选择"已报废"：系统展示报废信息表单（报废原因、报废说明、确认复选框）
11. 设备管理员填写完成后点击"确认变更"
12. 系统校验通过后，更新设备状态字段，记录状态变更日志
13. 若维修来源为医生报修：系统同步更新报修记录状态为"已受理"，向报修医生推送受理通知
14. 系统更新页面，设备展示新状态标签（维修中=橙色 / 已报废=灰色）
15. 设备修复后，设备管理员在维修设备详情页点击"维修完成"
16. 系统展示维修完成确认表单（实际天数、维修结果、费用、备注），填写后设备状态变更为"离线"
17. 若维修来源为医生报修：系统将报修记录状态同步更新为"已完成"，
      向报修医生推送完成通知

### 异常流程

- 4a. 报修记录详情加载时设备数据获取失败 → 报修详情仍可正常展示，
  "设备近期运行数据"区域显示"加载失败"
- 6a. 报修对应的设备已被他人先受理 → 提示"该设备已被受理维修，报修状态已变更"，刷新列表
- 6b. 医生报修的故障描述与实际情况不符 → 设备管理员在维修说明中补充实际故障情况，
  正常受理，不受影响
- 9a. 目标状态选择"维修中"但设备已在维修中 → 提示"该设备已在维修中，请先完成当前维修"
- 10a. 选择"已报废"但设备当前为"维修中" → 弹窗提示"设备正在维修中，确认直接报废？"
- 10b. 报废确认复选框未勾选 → "确认变更"按钮保持禁用
- 11a. 设备在质保期内操作报废 → 额外提示"仍在质保期内，建议先联系厂商售后"
- 12a. 数据库操作失败 → 提示"操作失败，请稍后重试"，状态保持不变

### 业务规则

1. 设备状态流转：
   - 在线/离线/异常 → 维修中 → 已修复（变为离线等待上线）
   - 在线/离线/异常/维修中 → 已报废（终态，不可再变更）
2. 维修来源有两种：设备管理员定期巡检主动发现、社区医生使用中发现后提交报修（UC-DOC-08）
3. 维修原因为"医生报修"时，维修工单必须关联报修记录编号
4. 已报废设备不物理删除，保留在数据库中作为历史归档
5. 每次状态变更必须记录完整日志（操作人、操作类型、变更前后状态、原因、时间）
6. 质保期内维修费用标记为"质保期免费"
